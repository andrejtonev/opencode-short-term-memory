# STM Feature Matrix

Current source operational comparison for **RC11 (`1.4.0-rc.11`)**, reviewed on 2026-10-26, with published RC9 differences identified explicitly. Publication and exact-archive qualification are recorded in [RC Readiness](RC-READINESS.md). V1 and V2 share configuration and memory utilities but use different runtime APIs. Implementation descriptions do not establish live qualification. Historical records retain their original release identities.

RC11 branch-review fixes have separate source regression coverage; the frozen RC10 qualification does not cover those later changes. See [Acceptance Runners](ACCEPTANCE-RUNNERS.md) for maintained checks and historical probes.

The current development source atomically initializes only missing memory files and preserves existing empty files. V1 active mode uses message-aware NoReply injection even with the legacy selector enabled. V2 active updates and clean-to-active fallbacks install a temporary generate hook for a uniquely marked STM request, remove its tool definitions, and dispose the hook when the operation settles. Unmatched requests keep their tools and native context. The native OpenCode 2.0.32 deterministic check proved tool removal, concurrent-request preservation and disposal; it does not qualify live providers or the published archive.

## Generation

Sources: [V1 summarizers](../src/summarizer.ts), [V1 chunk lifecycle](../src/memory-lifecycle.ts), [V2 updater](../src/v2-memory-update.ts).

| Capability                | V1                                                                                                                                                                                                                                                        | V2                                                                                                                                                                                                                                               |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Clean generation, default | Fresh temporary side session for each attempt; generated assistant response with summarizer system prompt and text.                                                                                                                                       | Standalone `context.generate.text({ prompt, model }, { signal })`; **no side session**.                                                                                                                                                          |
| Clean isolation           | No main-session history is supplied as session context; the host project instance, other plugins and host-provided instructions can still apply. Summaries stay out of the main chat.                                                                     | Direct text request contains the summarizer prompt, not main-session instructions/history as session context. Isolation does not mean a separate host session.                                                                                   |
| Active generation         | Generated prompt delivered into the active session, with summarizer system text; may appear in chat.                                                                                                                                                      | `context.session.generate({ sessionID, prompt }, { signal })`; session-bound, not clean-room generation.                                                                                                                                         |
| Inherited model           | Empty `memoryModel` omits the request override; a fresh clean side session therefore relies on host model resolution, while omission does not assure inheritance for an active invocation.                                                                | Clean explicitly passes the current input/history model; active uses session generation without a model argument.                                                                                                                                |
| Explicit `memoryModel`    | Valid `provider/model` passed in clean and active requests.                                                                                                                                                                                               | Valid override supported in clean only. Active plus override skips with `active_model_override_unsupported`; malformed nonempty override errors.                                                                                                 |
| Retries                   | `1 + sideSessionRetries` clean attempts; classified permanent provider failures stop retries. Other caught clean failures, including timeouts, may retry. Active has no equivalent retry loop.                                                            | `1 + sideSessionRetries` attempts in clean **and active**, only for settled `V2TransientGenerationError` or malformed-output errors, within one chunk deadline. Arbitrary errors are not automatically transient.                                |
| Active fallback           | Opt-in after exhausted clean failures, excluding classified permanent provider failures; retains configured model override.                                                                                                                               | Opt-in, at most one active fallback after settled retryable clean failures, only with no explicit override and time remaining.                                                                                                                   |
| Timeout/cancellation      | Clean prompt has a 90-second abort timer and best-effort server abort. No equivalent explicit deadline for active generation or temporary-session creation/deletion. Lifecycle invalidation blocks stale persistence, not necessarily ongoing generation. | Default 90-second **per-chunk** deadline shared by retries/fallback. Timeout/cancellation requests abort, prevents late-result persistence and does not retry/fallback. Host work may continue; generation reservation remains until settlement. |
| Output validation         | Assistant envelope, nonempty text, memory header and no raw template markers; normalized chunk also requires a section heading.                                                                                                                           | Nonempty text, memory header, all five required headings and no raw template markers before normalization. Validation is structural, not semantic correctness.                                                                                   |
| Cleanup                   | Best-effort immediate deletion, persisted `side-sessions.json` tracking and startup orphan scan.                                                                                                                                                          | No temporary sessions to clean. Disposal aborts plugin lifetime and unregisters hooks/tools/commands/RPC.                                                                                                                                        |

Native V1 clean side sessions retain normal tool definitions with approval permissions. STM rejects filesystem, shell, plugin and MCP tool execution in its native pre-execution guard. Unguarded standalone runtimes instead disable tools in the request. V2 clean generation uses the direct text API. Published RC10's active-summary tool isolation remains unqualified; the later development request fence has the separately scoped deterministic native evidence described above.

Both prompts treat existing memory and conversation as data, prioritize user instructions and conservatively retain prior facts. Model obedience, faithful retention and prompt-injection resistance are not guaranteed by these policies.

`maxMemoryLength` is **not a strict stored-file byte ceiling**: shared normalization keeps the line crossing its character target and adds the format marker. Injection payloads are character-clipped; prompt scaffold/format/preamble overhead is additional.

### V1 Reset Boundary

RC10 stores a distinct V1 boundary at `<memoryDir>/v1-reset-boundaries/<session>.json`. Reset validates SDK history before erasing memory and anchors through its latest durable record after excluding STM generation prompts/replies; empty history permits future records. Malformed/unavailable history refuses reset, while malformed boundary files or missing anchors pause later summarization. Post-reset updates retrieve full history to find the anchor before applying the post-boundary look-back cap. Existing RC9 resets are not migrated automatically. Conversation history is not erased, so new messages can reintroduce earlier information. Prepared file writes and guarded rollback are not a crash-atomic or cross-process transaction. These changes are not included in or qualified for the RC9 archive; RC10 evidence is linked in [RC Readiness](RC-READINESS.md).

## Current Release Qualification

RC10 passed source checks (1,216 pass / 3 skip / 0 fail), exact-archive fresh-consumer/declaration checks, native V1 menu and populated-conversation reset checks on `1.18.35`, and native V2 dialog checks on `2.0.32`. The registry archive matches the frozen bytes. Native UI checks used the extracted archive with a repository dependency junction, separately from fresh-consumer installation. This does not prove live V2 generation, Ubuntu/Lima or a fresh native registry installation. A user's general manual success on another V1 OpenCode 1.18 machine remains separately scoped.

The published RC9 README still contains preparation status and RC8 installation examples. RC10 ships corrected instructions that pin RC10. The frozen RC9 package remains unchanged.
